# 当前能力与控制边界

Harness 由宿主 agent 协调，Python 工具负责记录、执行和结构化检查。下表区分产品实现与验证范围；具体设备、外部仓库版本和测量证据由用户项目保存。

| 能力 | 当前实现 | 验证与边界 |
| --- | --- | --- |
| 项目与生命周期 | projectctl 管理 owner、worktree、冻结/归档/恢复 | CPU 临时 Git 仓库覆盖；外部 writer/job 状态由宿主核实 |
| 节点交接 | TASK/RESULT @4、candidate@2、环境与标杆模板 | 结构字段由程序检查；PROJECT 自然语言规则、科学解释和实际授权由协调者核验 |
| 本地执行与评测 | runctl 管理前台进程；evaluate 执行冻结参考、比较器与适配器并生成证据 | 真实 CPU 子进程覆盖正确/错误候选；torch_npu 接线使用 CPU mock，设备闭环仍需验收 |
| 接收与候选晋升 | 校验候选/全部必选输出/样本/回执；accept 与 promote-candidate 分开 | best 是协调者选定的合格且可比较候选；工具没有自动最快候选排序器 |
| 依赖队列 | search@2 显式依赖、冻结输入、原子准入、工作空间占用及释放 | CPU 集成覆盖；宿主派发和跨项目设备互斥仍由执行环境承担 |
| 执行控制 | control 保存 run 步数、预留、job 观察与结算；设备最终回执待确认时继续占用资源 | 合作工具内原子更新；宿主问询等控制动作另行计数 |
| 搜索与知识 | 机制历史、不可变 hot 修订、带批准来源的 cooled 及失效后继 | 机制计划可选；语义查重、消融价值与批准真实性由协调者/宿主核验 |
| 安装生命周期 | 技能副本安装、清单、升级计划、恢复与回滚 | 隔离目录测试；npm/CLI、卸载和独立发布待完成 |
| 设备与仿真扩展 | torch_npu 测量/诊断方法、采集脚本与离线解析 | 通用设备后端、完整 ABI 导出、simulator 和完整执行矩阵待建设/验收 |

## 四类操作对象

| 类型 | 对象 | 谁能改变、何时改变 |
| --- | --- | --- |
| 冻结输入 | TASK、evaluation-plan、参考/比较器/case/协议、评测代码身份、候选快照 | 协调者在准入前固定；执行节点只读。改变目标或规则时保留旧记录，安全关闭受影响任务后建立新任务 |
| 允许编辑 | TASK 白名单内的源码 worktree、独占 build/cache、尚未终结的 RESULT 与运行产物 | 所属执行者在既定操作和预算内修改；候选和终态证据冻结后使用新身份 |
| 保留历史 | 账本事件、候选谱系、已接收 RESULT、hot/cooled 修订、失败与关闭记录 | 通过工具追加事件或后继版本；历史失败、审批来源和证据摘要保留，修订不抹掉原记录 |
| 用户决定 | 目标/验收范围变更、额度增加、知识冷却批准、推送/合并/发布及破坏性操作 | 使用真实且覆盖当前动作的用户决定；既有授权直接复用，工具记录不代替授权真实性 |

这些约束面向合作开发。文件锁、摘要和路径登记帮助工具拒绝冲突与漂移；任意同账号 shell 的权限隔离需另建执行后端。

## 唯一事实源与摘要

- `project.json` 保存项目身份、owner、生命周期和已登记仓库。
- `search/tree.json` 保存搜索节点、run/candidate、接收/关闭、best、知识引用，以及启用后的 scheduling/control。
- 冻结的原始证据与回执支持验收结论；Markdown 描述只在其对应范围内提供解释。
- STATE、EXPERIMENTS、AUTOMATIC、RESOURCE_USAGE 保存导航、决定和账本投影。control 启用后，资源余额以程序账本为准；摘要记录所依据的事件水位，恢复只补未完成的投影。
- 未启用 control 的旧任务继续使用原手工资源账本，安全收尾后显式接入；恢复不把两份余额叠加。

## 两类步数

`automatic` 的 `max_steps` 限制宿主控制动作，包括节点工作以及独立的接收、恢复或问询。原节点的重连与收尾沿用原步骤。程序 `control.step_limit` 限制已准入的 run 数；队列准入或批次成员分别占一步，失败不退步。

程序不能自动观测所有宿主动作。协调者在 AUTOMATIC 记录宿主总计数，并引用 control 的 run 计数和事件水位；新动作同时满足宿主上限与程序额度。两类计数分别标注，恢复保留各自已用量。独立后台调度、统一自动采集宿主动作计数仍属后续能力。

## 接收、best 与最终交付

accept 表示本节点满足适用交付契约；性能未达标的有效初版或思路失败可保留并进入后续分析。promote-candidate 重新检查合格性和比较契约，best 的优劣取舍仍由协调者按预先固定的逐 case 规则记录理由。代码只通过精度、code-only/collect-only 的完成状态或一次较快样本，都不足以直接宣称最终最优。

最终交付核对当前目标、完整必选结果、已知退化与未验证范围。真实设备支持按芯片、工具链和 local/remote × host/docker 逐组合验收；CPU 或 mock 通过只证明相应协议路径。
