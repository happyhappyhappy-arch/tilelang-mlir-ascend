# Operator Harness TODO 路线图

目标是让新 agent 在独立安装环境中，仅凭任务与落盘产物完成 TileLang 算子的开发、实卡验证、优化和交付。首批语言为用户指定版本的 TileLang，首个宿主为 Codex；当前实现与验证范围见 [能力表](capabilities.md)，产品要求见 [需求](REQUIREMENTS.md)。

## 如何使用清单

每个 T 编号代表一项可单独安排的工作；完成交付物并取得对应验收证据后勾选。批次表示优先级，实际开工以任务依赖为准，互不依赖的任务可以并行。未指定时间和负责人，避免把尚未确认的投入写成承诺。

已有能力的增强任务只补齐所列缺口。CPU 或 mock 测试通过不代表实卡验收完成；具体机器、外部版本、执行记录和证据保存在 `.workspace/`，产品清单保留通用任务与完成条件。

## 第一批：恢复与首个实卡闭环（M1 / M2）

先完成一个选定芯片、工具链和执行组合的闭环。此阶段使用现有 evaluation-plan 与冻结适配器，完整 ABI 自动导出在第二批交付。

- [ ] **T01 — 补齐跨层中断恢复演练。** 依赖：无。
  交付：围绕启动、进程回执、设备最终回执、资源结算、accept、环境发布和摘要更新的故障注入用例。
  验收：在各持久化边界中断后，由新进程沿原 request/job 恢复；不重复执行、重复扣额或提前释放 unknown 作业资源；保留失败与实际副作用记录。

- [ ] **T02 — 完善只读状态汇总与摘要重建。** 依赖：无，可与 T01 并行。
  交付：统一展示在途/未知作业、未结预留、待确认回执、知识失效、摘要漂移及事件水位；为宿主动作和用户决定保留独立于摘要的持久记录，提供可幂等补写的摘要路径。
  验收：删除或滞后 STATE/AUTOMATIC/RESOURCE_USAGE 摘要后可从对应事实源恢复；只读查询无写入；宿主控制步骤与程序准入 run 数分别显示、分别检查预算，不用 run 数推算问询等宿主动作。

- [ ] **T03 — 固定首个实卡验收场景。** 依赖：无，可与 T01/T02 并行。
  交付：一个代表性算子、独立正确性参考、边界 case、性能基线或明确替代目标，以及选定设备环境的最小编译/运行探针；沿用已有环境选择。
  验收：正确候选、已知错误候选、精度正确但未达性能目标的候选均有明确预期；语义、输出、计时范围、预算和停止条件在执行前冻结。所有具体选择落入用户项目。

- [ ] **T04 — 随包提供首个设备执行后端。** 依赖：T03。
  交付：按 [复用计划](REUSE_PLAN.md) 适配可用的 Onboard/DeepJIT 能力，提供环境探测、编译、提交、查询、取消/超时和产物回收；将物理设备互斥与最终回执接入现有控制账本。
  验收：独立安装不依赖作者个人技能；控制端、传输、worker、guard 与设备作业状态分别保留；请求可重查，unknown 保留占用；设备 busy 时间与完整 guard 资源用量分别记录。

- [ ] **T05 — 验收设备正反例、共享资源与故障路径。** 依赖：T01、T04。
  交付：在 T03 的环境中执行完整精度、约定性能/诊断和故障矩阵，加入两个项目共享同一物理设备的排队场景。
  验收：错误候选不进入正式计时；有效但未达目标的结果如实保留；初始化失败、非零退出、超时、断线和取消可追踪并恢复；两个项目不重叠占用独占设备，回执不被后续持锁者覆盖。

- [ ] **T06 — 完成新 agent 冷启动接续与最终复验。** 依赖：T02、T05。
  交付：在独立安装目录中，让新 agent 仅凭项目根、TASK 和前序产物接续；覆盖一次 analysis → develop → analysis，并独立复验交付候选。
  验收：不依赖原聊天或私人路径，不重复启动/结算；全部必选输出、原始样本、选择理由、退化 case 和限制可复查；仅精度任务不被强加性能测量。

本批完成条件：T01–T06 全部通过。能力表只声明已验收的设备与执行组合。

## 第二批：完整执行包与评测契约（M1 / M2）

T07 可与第一批并行设计；T08/T09 在选定工具链上逐步接入。

- [ ] **T07 — 定义版本化候选执行包。** 依赖：无。
  交付：描述语义、shape/dtype/layout/stride、输入输出容量、workspace 大小/对齐/别名/生命周期，以及多阶段依赖、同步、测量窗口和清理方式的契约。
  验收：字段有明确来源、必需条件与版本兼容规则；缺失、未知版本或不支持的能力可诊断；未编译字段保持未知，不以默认值假装已确定。

- [ ] **T08 — 从编译产物导出 ABI 与 launch 元数据。** 依赖：T03、T07。
  交付：导出源码/二进制摘要、编译器/目标/配置、入口/参数顺序、grid/block、mix mode、动态共享/local memory、launch API 与 stream；记录多阶段及辅助 kernel。
  验收：使用非零 local memory 和多阶段夹具核对导出值与 runtime 实参；新 agent 无需重推 ABI；具体外部工具链修订由项目选择。

- [ ] **T09 — 让设备 runner 直接消费执行包。** 依赖：T04、T08。
  交付：统一包的校验、传输、加载、launch、输出回收与清理，接入现有精度/性能证据链。
  验收：删除或改错必需 ABI/内存字段在设备执行前拒绝；完整算子与多阶段同步范围正确；case 数增加不导致状态无界保留；冷启动可从包重现正确结果。

- [ ] **T10 — 补齐编译缓存与跨环境产物失效规则。** 依赖：T09。
  交付：将源码、编译配置、目标、工具链和执行包身份纳入缓存与设备产物检查，明确迁移后重编译/重测范围。
  验收：同名文件内容变化、工具链/设备/容器变化不会误用旧产物或旧证据；可复用项有明确依据；仅资源余额变化不使环境身份失效。

- [ ] **T11 — 实卡验收标杆移植及无性能源码路径。** 依赖：T06、T09。
  交付：分别覆盖 port-baseline 和 initial-and-validate；验证 absolute/model/none 目标，补齐模型工作量、流量/计算/同步假设、参数来源与适用条件。
  验收：参考经独立小样例或不变量核查；预测、参考和实测分别报告；模型与容限在采样前固定，目标变化生成新修订；仅精度任务可完整交付。

本批完成条件：T07–T11 全部通过。首个设备闭环能直接消费可复现执行包。

## 第三批：长期搜索与候选选择质量（M2 / M6）

复用现有搜索树、机制历史与 hot/cooled 记录，增强需要程序检查的准入和交付规则。

- [ ] **T12 — 为大预算尝试增加机制准入条件。** 依赖：T06。
  交付：可配置的大预算触发条件，要求记录预期机制、历史近邻、反证、验证方法和停止条件。
  验收：没有新依据的相同失败方案不会反复消耗预算；有新证据的重试可说明差异；小规模探索保留低成本入口，触发门槛由项目确定。

- [ ] **T13 — 对复合优化执行有界消融与简化。** 依赖：T12。
  交付：为多个同时变化的因素生成消融/裁剪任务，使用已有依赖队列管理结果。
  验收：结论能区分各因素贡献与交互；同等质量时有简化选择依据；保留失败与无收益结果；追加实验遵守原预算和停止条件。

- [ ] **T14 — 建立来源复查与知识更新触发规则。** 依赖：T02、T12。
  交付：按来源版本、环境变化或项目设定的有效期触发 baseline/知识复查，记录刷新水位、受影响结论及后继版本。
  验收：过期来源不会无提示继续支持新决策；旧比较契约与失败证据保留；知识冷却复用覆盖当前动作的真实批准，远端发布授权单独记录。

- [ ] **T15 — 固定多 case 排名与交付复验规则。** 依赖：T06、T11。
  交付：在现有逐 case mean/median 阈值之外，为确有需求的业务权重、允许退化和汇总统计定义明确契约；记录 best 选择理由与独立复验结果。
  验收：所有 case 和原始样本参与预定规则，统计口径与允许偏差在采样前固定；不同指标不可混比；报告排名波动和退化，不因一次更快样本宣称最优。

本批完成条件：T12–T15 在一个有实际优化空间的任务中验证，能说明搜索成本、选择依据和最终收益。

## 第四批：CLI、分发与安装生命周期（M3 / M5）

T16/T17 可与设备建设并行；独立发布只包含已经验收的能力子集。

- [ ] **T16 — 提供版本化 npm 包与 init 入口。** 依赖：无。
  交付：封装已有源码安装器，通过带版本号的 npx CLI 安装 Codex skills；分开管理产品文件、用户配置与实验产物。
  验收：从本地打包产物初始化空目录，无需 harness 源码 checkout；安装幂等、冲突可见；包内不包含私人路径、运行记录或固定外部 commit。

- [ ] **T17 — 提供只读 doctor。** 依赖：T16；设备检查复用 T04，未提供的后端明确报告。
  交付：检查安装完整性、宿主接入、Python/Node.js、所选工具链与环境配置，并给出可执行的缺口定位。
  验收：对缺失依赖、错误版本、不可达环境和未支持组合给出准确诊断；检查不隐式安装依赖、启动设备任务或改变用户配置。

- [ ] **T18 — 实现卸载与配置迁移。** 依赖：T16。
  交付：基于受管清单卸载产品文件并迁移版本化配置，复用升级事务与回滚机制。
  验收：保留用户修改、额外文件、源码 worktree 和实验记录；重复执行及中途失败可恢复；旧配置不可自动迁移时保留原件并报告原因。

- [ ] **T19 — 保存仍在使用的工具束并验证升级接续。** 依赖：T01、T16。
  交付：按在途任务引用保存所需评测代码和契约版本，明确工具束选择、升级兼容与安全回收条件。
  验收：升级后原任务可使用原代码完成接收/结算；不兼容时沿原流程安全关闭后建新任务；卸载/回收不会删除仍被引用的工具束。

- [ ] **T20 — 完成首个独立发布验收。** 依赖：T16–T19；设备能力纳入发布时同时要求 T06，执行包能力纳入时要求 T09。
  交付：确定包名、许可证、发布账号、支持平台和运行时范围，准备版本说明及发布检查；按已有发布授权执行。
  验收：发布前用真实打包产物验证安装、doctor、最小工作流、升级/回滚及卸载；发布后从实际分发源复验。未验收的后端在文档与工具中明确标注。

本批完成条件：独立用户可通过分发包安装、诊断、完成所声明流程并安全升级或卸载。

## 第五批：执行矩阵、仿真与工具接口（M4）

按实际任务选择扩展方向。仿真建设与其余设备组合不依赖 npm 发布，也无需互相等待全部完成。

- [ ] **T21 — 逐项补齐其余设备执行组合。** 依赖：T05、T09。
  交付：在首个组合之外，为 local/remote × host/docker 的每个剩余组合建立独立任务和支持记录。
  验收：逐组合核查编译/运行位置、架构、镜像、挂载、设备映射、退出传播与产物回收；分别通过正确/错误候选、超时/断线/取消和恢复，不能外推支持范围。

- [ ] **T22 — 定义 simulator 环境并接入首个执行后端。** 依赖：T07；T04 已提供时复用适用接口，否则独立定义仿真任务接口。
  交付：共享仿真环境描述、依赖/身份探针，以及编译、提交、查询、取消、超时和产物回收能力；选择一个明确的仿真执行组合。
  验收：新 agent 可复现最小 case；状态与部分产物可恢复；实卡和仿真不相互继承授权或验证状态；其余仿真组合各自保留待验收任务。

- [ ] **T23 — 打通仿真/流水采集到 analysis 的证据链。** 依赖：T22。
  交付：绑定候选、编译产物、采集配置、解析器和覆盖范围的 trace/指标产物，接入 collect-only → analysis 交接。
  验收：源码或已有 trace 可直接分析；残缺 trace 标明缺口；模型周期、采集耗时与实卡性能分别解释；结论可追溯原始数据。

- [ ] **T24 — 按接口需要提供 MCP 外层。** 依赖：封装设备后端要求 T05，封装 simulator 要求 T22。
  交付：先评估 simulator 的 MCP 接入价值，再按需求暴露环境检查、提交、查询、取消和产物读取；Onboard 是否封装另行决定。
  验收：真实客户端完成长任务查询、失败/取消与结果回收；大体积日志通过产物引用读取；MCP 部署位置与实际执行位置分别配置，不在外层重复工作流决策。

本批按组合逐项验收；“全部矩阵完成”要求实卡和仿真各自覆盖四种组合。

## 按需任务：扩大项目与宿主范围（M6）

以下条目保留为 backlog。出现明确使用场景后再选择开工，并拆成一个具体适配目标，不作为首个可用版本的前置条件。

- [ ] **T25 — 支持 subproject 与父子项目协作。** 前置：有整网或多算子协作需求，且 T06 已完成。
  交付：父子契约、融合与依赖、源码/记录归属、预算和生命周期设计，以及对应入口。
  验收：子项目可独立恢复；父项目能追踪依赖与总体验收；冻结、归档、恢复和失败不会破坏其他子项目。

- [ ] **T26 — 增加算子、数据与设备覆盖。** 前置：T06，按新场景选择必要的 T09/T21。
  交付：为新增算子、dtype/layout、动态 shape 或芯片/工具链分别建立兼容性任务与边界 case。
  验收：每个新增范围都有独立参考、正反例和真实执行证据；区分按 shape 重新 JIT 与同一二进制的运行时动态 shape；既有支持范围保持回归通过。

- [ ] **T27 — 评估并接入下一种语言或宿主。** 前置：明确需求；新语言适配 T07/T09 契约，新宿主沿用 T16 的产品/配置边界。
  交付：先为一个目标做适配设计；语言提供编译/执行包，宿主提供工具调用、授权来源、委派与恢复接口。AscendC 和其他宿主均按需求选择。
  验收：同一组契约正反例在新入口通过；生成的 AscendC 产物与独立 AscendC 开发入口不混为一谈；不引入无关的工作流运行时依赖。

- [ ] **T28 — 根据观测成本决定是否增加环境自动化或后台调度。** 前置：T06，已有明确的环境重复准备成本或宿主吞吐瓶颈。
  交付：分别评估环境自动准备、宿主动作自动计数和独立后台服务，选中项另开有界实施任务；维持现有宿主队列可用。
  验收：新能力能量化减少准备成本、改善任务完成率或吞吐；权限、预算、恢复和可观测性不退化；没有收益依据的方向保留为未实施。

## 建议立即启动的任务

首轮并行推进 **T01、T02、T03**；执行包设计 **T07** 可同步进行。T03 固定场景后接 **T04 → T05 → T06**，形成首个可独立复现的实卡闭环。编译器导出按 **T07 → T08 → T09** 推进，随后完成 **T10/T11**。

人力有限时先保留第一批，T16/T17 和后续扩展顺延。真实设备暂不可用时继续 T01/T02/T07 与安装分发工作，设备任务保持待验收状态。

## 更新约定
